# C2.0 · Аналіз: аварійне відновлення журналу операцій і єдиний власник запису

Лише аналіз. Код рушія, Actions, Pages, `engine_owner` не змінювались і не активувались; прототипу леджера/власника не створено (це C2.3 і C2.4).
Єдиний експеримент — вимір вартості `fsync` на цій машині (розділ 2.4); це не перевірка VPS.

## 1. Що є зараз (прочитано в коді, без змін)
| Елемент | Як працює | Слабке місце для Live Trading 2.0 |
|---|---|---|
| Запис файлів даних | `common.write_json`: запис у `*.tmp` → `os.replace` (атомарна заміна); без `fsync` | після аварії ОС файл може бути порожнім/старим; для основного режиму достатньо (щоразу перераховується), для леджера — ні |
| Стан паперового рахунку | `_paper*.json` — **знімок**, не журнал; журнал `paper_events*.json` обрізається до 40 подій на правило | повної історії в рушії немає: єдиний довгий журнал — архів `paper_archive/` (копіюється з джерел, не є джерелом істини) |

## 2. Аварійне відновлення журналу операцій (цільовий леджер)

### 2.1 Формат і протокол запису
- Append-only JSONL, один рядок на операцію: `{"seq", "batch", "op_id", "epoch", "ts", "mode", "payload", "crc"}`; `crc` = CRC-32 канонічного рядка без поля `crc`; додатково ланцюжок `h = sha256(h_prev + канонічний_payload)` — виявляє усічення й підміну в середині.
- `op_id = sha1(режим | гаманець | правило | монета | сторона | свічка_або_час_тіка | початок_раунду)`; для тіків у режимі B додається лічильник у межах мілісекунди. Це ключ ідемпотентності: повторне обчислення тієї самої угоди дає той самий `op_id`.
- **Write-ahead**: спочатку запис батчу в леджер (`fsync`), потім оновлення стану в пам'яті, потім (періодично) знімок. Кожен крок рушія (до 48 рахунків) — один **батч** із маркером завершення `batch_end`; батч без маркера при відновленні відкидається цілком, крок обчислюється заново (рушій детермінований).
- Сегменти по добі (`ledger-YYYYMMDD.jsonl`), манифест із хешем кінця кожного сегмента; старі сегменти стискаються, хеш-ланцюжок переходить через сегменти.
- Знімок стану: `state-<seq>.json` атомарно (`tmp` → `fsync` → `replace` → `fsync` каталогу на Linux), поля `ledger_seq`, `ledger_h`, `config_sha`, `epoch`; зберігаються три останні.

### 2.2 Алгоритм відновлення при старті
1. Прочитати сегменти по порядку; кожен рядок: валідний JSON, `crc`, суцільність `seq`, унікальність `op_id`, ланцюжок `h`.
2. **Рваний хвіст** (останній рядок обірваний, решта цілі): копія хвоста в `.torn`, усічення до останнього повного батчу з `batch_end`.
3. **Пошкодження всередині** (інший невалідний рядок): сегмент у `.bad`, відновлення від останнього знімка, чий `ledger_h` збігається з ланцюжком до місця пошкодження; решта операцій відновлюється повторним обчисленням з REST-свічок (не вигадується); сповіщення оператору.
4. Завантажити найновіший знімок, перевірити `ledger_seq ≤ max_seq` і `ledger_h` = хеш ланцюжка в цій точці. Якщо знімок «попереду» леджера (неможливо за WAL, але можливо при втраті диска) — знімок недійсний, береться попередній.
5. Застосувати хвіст леджера (`seq > snapshot.seq`) чистою функцією `apply(op)`; перевірити інваріанти (позиції збігаються з останньою подією монети; `eq > 0`; відсутні дублі `op_id`).
6. Підключити WebSocket, виконати REST-дозавантаження від курсорів, продовжити цикл. Операції, які вже є в леджері, пропускаються за `op_id`.

### 2.3 Аварії по точках (що буде і чим перевіряється)
| Момент аварії | Наслідок | Поведінка | Тест (C2.3) |
|---|---|---|---|
| до запису батчу | слід відсутній | повторне обчислення дає ті самі операції з тими самими `op_id` | `kill -9` у 20+ випадкових точках: результат = безперервному |
| під час запису рядка | рваний хвіст | усічення до останнього `batch_end` | усікати файл на кожному байті останнього батчу |
| після запису, до оновлення стану | стан відстає | застосування хвоста | перерізати між кроками |
| після оновлення стану, до знімка | знімок старіший | застосування хвоста від знімка | те саме |
| повтор запису (ретрай) | дубль | `has(op_id)` → пропуск | повторити батч ×5 |
| диск заповнений / помилка запису | неможливо зафіксувати | стан не змінюється, рушій у режимі «лише читання» (потоки приймаються, рішення не діють), сповіщення | емуляція помилки запису |
| стрибок системного годинника | `ts` немонотонний | порядок визначає `seq`, а не `ts`; рішення за часом біржі | зсув годинника в тесті |
| зміна `knowledge` під час роботи | інша поведінка | `config_sha` у кожному знімку/батчі; зміна = нова епоха/прогін | підміна конфігурації |
| пошкодження посередині файлу | розрив ланцюжка | кроки 3 з §2.2 | псування байта в середині |
| розбіжність леджера й опублікованих файлів | сайт бачить не те | публікація — похідна від леджера (Publisher), перевірка збігу кількості й ID `sim-…` | порівняння з архівом |

### 2.4 Вимір (цей комп'ютер, Windows, Python; не VPS)
200–300 повторів: додавання рядка ≈ 300 байт — без `fsync` p50 0,004 мс; з `fsync` p50 0,27 мс, p99 0,68 мс; батч із 10 рядків + один `fsync` p50 0,27 мс, p99 1,0 мс;
знімок 140 КБ (`tmp` + `fsync` + `replace`) p50 1,05 мс, p99 1,5 мс; перевірка 300 рядків (JSON + CRC) 0,76 мс. Висновок: батчевий `fsync` дешевий на цьому обладнанні; на VPS (мережевий диск) вартість може бути значно вищою: вимірюється у C2.3 перед вибором політики.

### 2.5 Сумісність з архівом і формами публікації
Існуючий ID події — `sim-` + `sha1(parts)[:16]` (двійники з суфіксом `~n`). Publisher має відтворювати ті самі ID для режиму A (інакше архів і «Жива стрічка» отримають дублі); для режиму B ID мають префікс `shadow:` і не потрапляють в основний архів. Перевірка збігу ID — окремий тест у C2.3.

## 3. Єдиний власник запису в основний стан

### 3.1 Загрози
1. **Два писачі** (Actions-симуляція і Live Engine) пишуть у один стан/гілку `data` → розбіжність, подвійні угоди.
2. **Race на гілці `data`**: `git push --force` з застарілої копії стирає чужі файли (гілка = один коміт, усе або нічого).
3. **Split-brain після збою**: стара копія Live Engine «оживає» й продовжує писати.
4. **TOCTOU**: рушій перевірив прапор, власник змінився, запис відбувся.
5. Випадковий запис тіньового процесу в основні файли.

### 3.2 Механізм (проєкт; нічого не активовано)
- **Прапор власника** `engine_owner ∈ {actions, live2}` і лічильник `epoch` (монотонний) в одному файлі (місце розміщення — рішення C2.4: гілка `data` як похідний факт + локальний файл VPS як первинний).
- **Передача власності — двофазна**: (1) `draining`: жоден не пише основний стан; перевіряється, що останній стан збігається з хешем передачі; (2) `epoch+1`, новий власник; відкат симетричний. Кожен запис леджера й кожен опублікований файл несе `epoch`; споживачі відкидають менший.
- **Оренда процесу Live Engine**: `engine.lock` = `{pid, host, boot_id, epoch, lease_until}`; серцебиття 10 с, оренда 60 с; перехоплення лише після спливу оренди + пільгового інтервалу, за явною дією оператора або сторожа; запис завжди під утримуваним локом, прапор перечитується атомарно з записом (усунення TOCTOU).
- **Оптимістична конкуренція на гілці `data`**: майбутня заміна `--force` на `--force-with-lease=data:<очікуваний sha>` для кожного писача: несподіваний push → відмова й повтор; це **зміна workflow**, тому не робиться без вашого окремого погодження.
- **Actions-симуляція** при `engine_owner=live2` завершується без запису основного стану (потрібна невелика зміна коду, N2, пізніше).
- **Тіньова фаза**: власник лишається `actions`; тіньовий процес не має облікових даних для гілки `data` (фізичне розмежування) і пише лише у власний простір; тести ізоляції це перевіряють.
- **Відмова VPS при `live2`**: автоматичне повернення до Actions небезпечне (можливий split-brain); початково — сповіщення й ручне повернення; автоматика лише після окремого рішення та тесту.

### 3.3 Тести (C2.4)
Два процеси одночасно беруть оренду (лише один успішний); перехоплення прострочененої оренди; відкидання запису зі старим `epoch`; крах під утримуваним локом; зсув годинника для оренди (використовувати монотонний час локально); перевірка, що тіньовий процес без токена не може записати в `data`; сценарій двофазної передачі й відкату.

### 3.4 Відкриті питання для вашого рішення
Де первинне сховище прапора (VPS-файл чи гілка `data`); політика автоматичного відновлення після відмови VPS; прийнятна затримка передачі власності; чи потрібна зовнішня резервна копія леджера (де).
