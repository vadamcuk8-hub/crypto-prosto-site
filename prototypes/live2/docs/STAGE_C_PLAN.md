# Live Trading 2.0 · етап C: тіньовий рушій для 16 стратегій і 48 рахунків

Статус: прототип у `prototypes/live2/`, чинний рушій **не змінено**. Нічого не закомічено й не опубліковано.

## 1. Архітектура

```
Binance WebSocket (miniTicker + kline 15m/30m/1h/2h/1d, 10 монет)         Binance REST (klines, depth)
        │                                                                     │ (початкове завантаження, дозавантаження пропусків)
        ▼                                                                     ▼
   feed.py ── перепідключення, stale-контроль ──►  buffers.StreamMarket  ◄────┘
   (етап B)                                         • CandleBuffer на кожну (монета, масштаб), рівно 1000 свічок
                                                    • підтвердження закриття (kline x / REST), пропуски, дублікати, порядок
                                                    • readiness(): ready | wait | backfill | skip
                                                              │ ptf (вхід рушія)
                                                              ▼
                              driver.LiveShadow ── тригер: закриття свічки (debounce 0,3 с) або каденція
                                                              ▼
                              shadow.ShadowEngine ── engine_bridge ──► ЧИННИЙ agent_simulation.paper_wallets (без змін)
                                                              ▼          (load / write_json підмінено сховищем)
                                              state/<ім'я>/  (_paper*.json, paper_events*.json) + logs/ (метрики)
```

Принципи:
1. **Режим A («сумісність») не дублює логіку**: викликається той самий `paper_wallets`, що й в основній симуляції; три точки вводу-виводу рушія
   (`load`, `write_json`, `outlook_context`) на час виклику підміняються сховищем. Пісочниця `CRYPTO_DATA_DIR` ставиться ДО імпорту, тому
   справжня `data/` недосяжна навіть помилково.
2. **48 тіньових рахунків** = 16 стратегій × 3 гаманці (100 / 1 000 / 10 000 $, різні монети), ті самі `knowledge/simulation.json`
   (комісія 0,1 % + проковзання 0,05 % / книга заявок, мінімальний ордер 10 $, ваги, стопи, ті самі правила), але власний стан у `state/`.
   Основні баланси, позиції, історія й раунди не читаються й не змінюються.
3. **Режими не змішуються**: кожне сховище має `mode` (A або B); результати різних режимів і каденцій пишуться в різні папки.
4. **Рішення — лише за підтвердженими даними**: закрита свічка вважається такою після kline `x=true` або REST; інакше крок чекає, а за 1,5 с
   дозавантажує REST. Застарілі монети, мертве з'єднання, короткі ряди, пропуски → крок пропускається з причиною.
5. **Ізоляція**: немає запису в `data/`, гілку `data`, Actions, Pages; немає реальних чи (за межами тіньових) віртуальних операцій основної симуляції;
   Binance Testnet не використовується.

## 3. Безпечний рефакторинг чинного рушія (ПОТРЕБУЄ ОКРЕМОГО ПОГОДЖЕННЯ; нічого не змінено)

Режим A уже працює без змін рушія. Рефакторинг потрібен для режиму B (швидкі стопи/сканери) і щоб не залежати від підміни глобальних імен.

### R1. Витяг чистого кроку (поведінка не змінюється)
Зараз `paper_update(ptf, kb, now, tag)` (рядки 447–578 `agent_simulation.py`) складається з: ввід (`load` стану, журналу, `outlook_context`) →
**чистий розрахунок** (раунд, цикл по 16 правилах, `setup_step`, денні знімки) → вивід (`write_json` ×2). Пропонується:
```python
def paper_step(st, events, ptf, kb, now, cost, ctx):      # НОВА: рядки 459–574 без змін, без файлів
    ...                                                   # повертає (результат, st, events)
def paper_update(ptf, kb, now, tag=""):                   # обгортка з тією самою сигнатурою й тим самим результатом
    st = load(PAPER + tag) or {}; events = load(EVENTS + tag) or {}; ctx = outlook_context()
    cost = Costs(...)
    res, st, events = paper_step(st, events, ptf, kb, now, cost, ctx)
    write_json(PAPER + tag + ".json", st); write_json(EVENTS + tag + ".json", {k: v[-EVENTS_PER_RULE:] ...})
    return res
```
Лише переміщення коду. `paper_wallets`, `setup_step`, `decide`, `Costs`, `make_event` не змінюються.

### R2. Параметризація книги заявок (опційно)
`BOOKS` (глобальний словник) → аргумент `Costs(kb, cap, books)`; за замовчуванням бере `BOOKS`. Прибирає глобальний стан у тіньовому процесі.

### R3. Нові функції для режиму B (поряд, існуючі не змінюються)
`tick_exit(rule, co, price, ...)` (використовує вже чисту `setup_exit`), `scanner_tick(...)`, модель виконання (поріг / наступний тік / книга).
Запис результатів — лише в сховище режиму B.

### R4. Інкрементальні індикатори (лише якщо виміри вимагатимуть)
Зараз побудова входу (`scores_series` по 60 рядах) ≈ 93 мс, крок рушія ≈ 33 мс. Для частоти понад ~1 раз/с — перерахунок лише останньої свічки.

### Контрольні тести ДО і ПІСЛЯ рефакторингу (вже існують)
1. `tests/golden/replay24_digest.json`: SHA-256 повних результатів чинного рушія на знімку (24 год, крок 20 хв, 48 рахунків, 261 подія). Після R1 відбиток має збігтися **байт у байт**.

## 4. Режими перевірки
**A — сумісність (реалізовано).** Та сама модель виконання. Два підрежими: A1 — запуски за каденцією Actions (20 хв), A2 — частіші запуски.
Результат експерименту каденцій (14 год, реальні 1-хв ціни): 42 рахунки без сканерів **не залежать** від каденції (ті самі угоди, той самий капітал);
6 сканерних рахунків (`setup_live`, `setup_dip`) залежать: капітал змінився в 1–2 із 6, на каденції 1 хв +2 угоди (1 рахунок); макс. різниця капіталу 0,34 % депозиту (5 хв).
**B — прискорене виконання (ПЛАН, не реалізовано).** Окремі сховища; не змішувати зі статистикою A:
- B1 швидший Stop Loss / Take Profit за потоковою ціною; B2 Trailing Stop за піком із потоку; B3 реакція сканерів на кожному тіку;
- моделі виконання: за порогом (оптимістична), за наступним тіком, за доступною ціною книги (залежить від суми гаманця); кожна окремо.

## 5. Фінансова точність (порівняння з основною симуляцією)
Для кожного з 48 рахунків: equity, hold, кількість угод, відкриті позиції (ціна входу, пік, момент), крива (точка в точку), події (BUY/SELL, ціни, причини виходу,
`exit_info`), комісії/проковзання (в `eq` і `cost` подій). Режим A: допуск 0. Реалізований/нереалізований PnL і просідання рахуються тими самими функціями Analytics Pro
(`accountStats`/`periodResult`) з тіньових файлів; кожна розбіжність має мати пояснення (час, сканер, дані).

## 6. Надійність: матриця сценаріїв
| Сценарій | Механізм | Статус |
|---|---|---|
| Втрата WebSocket на закритті свічки | непідтверджене закриття → `wait` → `backfill` через 1,5 с; крок не стартує на непідтверджених даних | реалізовано; виявлено й виправлено живим тестом |
| Повторна подія | дубль закриття ігнорується; рушій пропускає свічки з `t ≤ co["t"]`; повтор кроку не створює угод | тести |
| Перезапуск процесу | стан у `state/`; відкриті позиції відновлюються; продовження збігається з безперервним | тест |
| Некоректні/застарілі ціни | NaN, ≤0, стрибок >15 %, запізнілий тік відкидаються й рахуються; мертве з'єднання → усі монети «застарілі» → пропуск кроку | тести |
| Пропущені свічки | пропуск → `backfill` без очікування; REST авторитетний | тести |
| Подвійні угоди | ідемпотентність рушія + контроль `now` | тест |
| Часові зони / мітки | усе в UTC мс; рішення за часом події біржі; `now` кроку = локальний UTC + зсув годинника | частково (потрібен NTP на VPS) |

## 9. Результати етапу C (до погодження рефакторингу)
- Режим A: тіньовий рушій (стан у пам'яті/`state/`) і ЕТАЛОН (справжній рушій на файлах) на 24 год відтворення (73 запуски, 261 подія): **0 розбіжностей у 48 рахунках**, криві збігаються точка в точку.
- Потік проти REST: вхід рушія зі стріму (miniTicker + kline) збігається з REST-входом на межах свічок; пропуск 50 хв із кількома закриттями виявляється й виправляється дозавантаженням.
- Живий прогін 45 хв (3 грубі обриви, зокрема на закритті 15m і 1h/2h): 46 кроків, 50 REST-дозавантажень, пропущених закритих свічок 0; після прогону відтворення тих самих кроків на повних REST-даних дало **ті самі угоди в усіх 48 рахунках** (35 подій), різниця капіталу медіана 0, макс. 0,17 % депозиту (рахунки з відкритими позиціями: ціна тіка проти 1-хв свічки).
- Виявлено й виправлено: крок рушія не може стартувати на непідтверджених закриттях (readiness: wait → backfill); додано таймер межі свічки (крок через 2 с після межі, а не через ≤60 с каденції).
- Виміри: побудова входу 95 мс, крок 48 рахунків 35 мс, запис стану 8 мс (разом ≈138 мс); CPU 0,8 % одного ядра, RAM 63 МБ; подія закриття свічки → завершення кроку ≈ 0,46–0,48 с (з них 0,3 с debounce).
